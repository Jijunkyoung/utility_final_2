## 1. 다루는 것이 '기한'이라는 점이 이 도구의 전부다

캠퍼스 유틸리티 설비를 한 사람이 여러 대 맡는다. 설비마다 법정검사 주기가
다르고 소모품 교체 시기도 따로 돈다. 지금은 엑셀과 기억에 의존한다.

그래서 첫인상은 "설비 대장을 만드는 일"이다. 대장은 어렵지 않다.
**어려운 것은 대장이 틀렸을 때 아무도 모른다는 것**이다.

이틀 밀린 날짜를 화면에서 알아채기는 거의 불가능하다. 그런데 이 시스템에서
이틀은 "법정검사 기한을 넘겼는가"를 가른다. 표는 멀쩡해 보이고, 기한은 지나간다.

이 저장소의 규칙이 대부분 **"모를 때 어떻게 하느냐"**에 대한 것인 이유다.

## 2. 검사 주기를 알려 주지 않는다

가장 넣고 싶었을 기능이고, 일부러 넣지 않은 기능이다.

같은 「보일러」라도 용량·종별·설치 장소에 따라 법정검사 주기가 다르다.
표에 숫자 하나를 미리 박아 두면 **그럴듯해 보이고, 그래서 아무도 다시 확인하지
않는다.** 틀린 주기로 법정검사를 놓치면 그건 실제 피해다.

지어낸 값이 위험한 것은 틀려서가 아니라 **확인을 멈추게 하기 때문**이다.

그래서 설비 종류를 고르면 `js/law.js` 의 `lawsFor` 가 **관련 법령 이름과
국가법령정보센터 검색 링크**만 준다. 주기는 사람이 확인해서 넣는다.
비어 있으면 「주기 없음」으로 표시되고 개요의 **확인 필요** 목록에 올라온다.

비어 있는 칸은 눈에 띈다. 지어낸 숫자는 눈에 띄지 않는다.

## 3. 자동 조회·무승인 자동 발송 대신, 승인 대기함

기획에 「법령 개정 모니터링」과 「알림 메일 발송」이 있었다. 둘 다 그대로
만들지 않았다. 서버와 인증키(또는 메일 계정)가 필요한데,
**사내 폐쇄망에서는 애초에 바깥으로 나갈 수 없다.**

바꾼 형태는 이렇다.

| 원래 요구 | 실제로 만든 것 | 어디 |
|---|---|---|
| 법령 개정 자동 조회 | 확인한 지 오래됐거나 대조할 값(사양·주기)이 빠진 설비를 **골라내고, 왜 골랐는지 적는다** | `Law.needsReview` |
| 알림 메일 자동 발송 | 임박 항목을 **승인 대기함**에 넣고 사람이 승인한 건만 사내 SMTP로 발송한다. SMTP가 없으면 문안을 복사한다 | 알림 화면 |

무승인 발송 대신 검토 가능한 대기함을 두므로 폐쇄망에서도 수동으로 사용할 수 있고,
**틀린 일정이 자동으로 퍼질 위험도 줄인다.**

## 4. 모르는 값을 0 으로 채우지 않는다

| 상황 | 흔한 처리 | 여기서는 |
|---|---|---|
| 이력의 금액을 모름 | 0 원 | **미상** — 합계에서 빼고 건수로 따로 |
| 비용 예측에 단가가 없음 | 0 원으로 합산 | **「셀 수 없었던 것」** 에 이유와 함께 |
| 마지막 검사일이 없음 | 오늘 기준으로 계산 | **「이력 없음」** — 날짜를 지어내지 않음 |
| 고지서에서 못 읽은 달 | 0 으로 그래프 바닥 | **행을 만들지 않음** + 몇 줄을 못 읽었는지 알림 |

0 으로 채우면 합계가 멀쩡해 보이고 **어디에도 표가 나지 않는다.**
예산을 실제보다 적게 잡거나, "3월에 전기를 안 썼다"는 그래프를 보고
있지도 않은 원인을 찾으러 다니게 된다.

**이 규칙이 실제로 결함을 하나 잡았다.** 첫 커밋에 기록이 남아 있다 —
`forecastYear` 에서 `Number(null) === 0` 이라, 단가를 모르는 항목이
**「셀 수 없었던 것」이 아니라 0 원으로 조용히 합산되고 있었다.**
화면으로는 절대 못 봤을 종류다. 합계가 그냥 조금 작았을 뿐이니까.

## 5. 날짜를 따로 검사한 이유

날짜는 **눈으로 검산하기 어렵다.**

가장 흔한 함정은 **말일**이다. 1월 31일 + 1개월을 그냥 더하면 2월에 31일이
없어 **3월 3일**이 된다. 검사 주기가 조용히 이틀 밀린다. 화면에서는 그냥
날짜 하나일 뿐이다.

그래서 판정하는 코드를 화면에서 떼어 순수 함수로 모았다 —
`js/schedule.js`(날짜) · `js/law.js`(법령) · `js/energy.js`(고지서).
셋 다 Node 에서 그대로 돈다. 화면은 판정하지 않고 그리기만 한다.

**깨뜨려서 확인했다.** 검사기를 만든 뒤 규칙을 하나씩 일부러 어겨 보고
전부 잡히는 것을 봤다 — 말일 처리 제거 / 이력이 없는데 「여유」 /
한 해에 여러 번 오는 주기를 한 번으로 / 13월 통과 / 요금 없음을 0원으로 /
법령표에 주기 지어내기. 여섯 가지 전부 잡혔다.

### 폐쇄망

바깥을 부르는 곳이 **한 군데도 없다.** 엑셀은 `lib/xlsx.full.min.js`,
PDF 는 `lib/pdf.min.mjs` + `lib/cmaps/`, 그래프는 라이브러리 없이 SVG 로
직접 그리고, 글꼴은 OS 기본이다.

cMap 을 함께 두는 이유는 한글 PDF 때문이다. 없으면 한글이 **빈 문자열**이 되어
"읽을 게 없다"로 끝난다 — 실패가 아니라 **빈 성공**으로 보이는 유형이라 더 나쁘다.

확인은 **localhost 말고 전부 차단한 크롬**으로 일곱 페이지를 실제로 열어서 했다
(`../hd-04/scripts/probe.mjs`). 거기서 뜨면 폐쇄망에서도 뜬다.

## 6. CI 를 붙였다

`test/logic.test.js` 에 61개가 있었지만 **사람이 손으로 돌려야 했다.**
안 돌리면 없는 것과 같다.

의존성이 없어 `npm install` 단계는 두지 않았다. 파일을 열면 그대로 도는 것이
이 저장소의 전제다. `supabase/`·`scripts/sqltest/` 단계도 뺐다 — 이 저장소에는
없다. **있는 것만 돈다.**

한 단계를 더 넣었다. 페이지 일곱 장은 `build.py` 가 굽는데,
**손으로 고치면 다시 구울 때 조용히 날아간다.** 그래서 CI 가 다시 구워 보고
커밋된 판과 다른지 본다.

```yaml
- name: 다시 구워도 같은가
  run: |
    python3 build.py
    git diff --exit-code -- '*.html'
```

고친 사람은 자기 수정이 사라진 것을 며칠 뒤에나 안다. CI 는 그 자리에서 말한다.

## 7. 화면 연기 테스트 — 규칙이 맞아도 볼 수 없으면 소용없다

규칙 61개가 전부 통과해도 `app.js` 의 오타 하나면 페이지가 빈 화면이 된다.
규칙은 맞는데 아무도 그것을 볼 수 없는 상태다. **파일을 읽어서는 안 잡힌다.**

「예시 자료 넣기」 한 번이 설비·소모품·이력·에너지를 모두 넣으므로,
그것을 누르고 일곱 장을 차례로 도는 것이 가장 넓게 훑는 길이었다.
자료가 localStorage 에 있으므로 같은 컨텍스트를 계속 쓴다.

가장 값어치 있는 단언은 §2 의 규칙을 화면에서 확인하는 것이다 —
설비 종류를 고르면 **법령 이름과 링크는 나오되 주기 숫자는 나오지 않는다.**
문서에 적어 두는 것과 화면이 실제로 그렇게 동작하는 것은 다른 얘기다.

**깨뜨려서 확인했다.** `innerHTML` 을 `innerHTMLL` 로 바꾸니
「예시를 넣으면 개요에 숫자가 나온다」가 실패했고,
**단위 테스트 61개는 그대로 통과했다.** 이 검사를 넣은 이유가 그 두 줄이다.

정적 서버의 MIME 표에 `.mjs` 를 넣어 두었다. 브라우저는 모듈 스크립트의
MIME 을 엄격히 검사해 `octet-stream` 이면 실행을 거부한다. 이 앱은 고지서
PDF 를 `lib/pdf.min.mjs` 로 읽으므로, 빠뜨리면 **원인 한 마디 없이 시간
초과로만** 끝난다(13번 저장소에서 실제로 겪었다). 시간 초과 대신 화면에
뜬 글자·못 내준 파일·콘솔 오류를 함께 적도록 진단도 붙였다.

## 9. Issue #2 — 설비 상세를 설비 ID로 묶었다

목록에 흩어진 설비·소모품·이력·매뉴얼·법령을 **설비 ID 하나**로 연결했다.
설비 목록의 상세 버튼을 누르면 기본정보·소모품·이력·매뉴얼·법령 다섯 탭이 열리고,
각 탭에서 추가·삭제한 자료는 같은 localStorage 저장 계층을 거쳐 새로고침 뒤에도 남는다.

자료 구조는 v2가 됐다. 기존 컬렉션은 유지하고 `manuals`, `lawReviews`를 더했으며,
문자열뿐이던 건물 개념은 `{id,name,x,y,w,h}` 좌표 레코드로 분리했다. 예전 v1 자료를
불러오면 없는 컬렉션과 건물 좌표를 채우되 원래 설비·이력 값은 버리지 않는다.

법령 탭은 설비명·종류·사양·용량·유량·압력·냉난방용량을 **검토 입력값**으로 보여 준다.
이 값으로 적용 여부나 검사주기를 자동 판정하지 않는다. 폐쇄망에서 외부 API를 호출하지 않고,
내장 후보표와 사용자가 기록한 사내 법령 자료 경로·확인일·메모·재검토 표시만 사용한다.

검증은 다음처럼 늘었다.

| 파일 | 무엇을 보는가 | 개수 |
|---|---|---|
| `test/logic.test.js` | 기존 규칙 + 법령·매뉴얼 분석·v1→v3 마이그레이션·설비 ID 필터·연결 자료 삭제·에너지 파싱 | 92 |
| `test/server.test.py` | 공유폴더 설정 · SQLite 생성 · 파일경로 안전성 | 3 |
| `test/smoke.browser.js` | 기존 화면 + 설비 등록·매뉴얼 분석·법령 비교·AI 설정·에너지 4개 그래프 | 51 |

## 10. 남은 것

- **기획서 원문이 없다.** `CLAUDE.md` 부록 A 가 비어 있다.
  지금 적힌 지시서는 구현에서 되짚은 것이라, **기획자가 요구했지만 구현되지
  않은 항목은 거기 없을 수 있다.** 원문을 받으면 대조해야 한다.
- **조감도 그림** — 건물 ID와 백분율 좌표 구조는 분리했다. 지금은 좌표에 네모를 배치하며,
  실제 조감도를 쓰려면 `img/campus.png`를 넣고 현장 도면에 맞게 좌표를 조정해야 한다.
- **사내 운영 전 확인** — 공유폴더 계정 권한, 서버 포트, AI 실행 프로그램과 외부 API 허용 여부를 보안 담당자와 확인해야 한다.

## 11. Phase 2 — 공유폴더와 문서 분석 기반

PR #3 병합 뒤 저장 구조를 v3로 올렸다. 브라우저는 UNC 공유폴더에 직접 파일을 쓸 수
없으므로 `server/facility_server.py`가 Windows에서 파일 저장과 SQLite 메타데이터를 맡는다.
설정 화면에서 서버 주소와 공유폴더 경로를 정하고 실제 시험 파일을 썼다가 지워 권한을 확인한다.

설비 등록 또는 상세에서 매뉴얼을 올리면 PDF·텍스트·CSV·엑셀 본문을 읽어 요약하고,
소모품 교체와 검사 문장에서 주기와 근거를 추출한다. 운전시간을 임의로 개월로 바꾸지 않으며,
사용자가 누른 제안만 소모품 또는 설비 검사주기에 반영한다.

법령 탭은 후보를 `lawDocuments`에 저장하고 원문·적용 조항을 함께 보관한다. 국가법령정보센터
API가 설정되면 사내 서버가 원문을 가져오며, 그렇지 않으면 사용자가 붙여넣거나 파일을 올린다.
비교표는 법령 요구사항, 설비 입력값, 결과, 근거, 조치사항을 보여 주되 규칙만으로 「충족」을
만들지 않는다.

AI는 세 경로다. 규칙 기반은 항상 가능하고, 로컬은 Ollama 호환 API, 외부는 OpenAI 호환 API를
사용한다. 자동 선택은 로컬을 먼저 시도하고 사용자가 외부 전송을 명시적으로 허용한 경우에만
외부로 넘어간다. API 키는 Git과 브라우저에 저장하지 않는다.

## 12. Phase 3 — 공용 데이터·담당자 대장과 보안 기본값

실사용 전 가장 큰 빈틈은 PC마다 자료가 따로 저장되는 점이었다. 사내 보조 서버에 공용 상태
테이블과 200개 버전 이력, 작업자 감사 기록을 추가했다. 브라우저는 자신이 읽은 버전을 함께
보내고, 다른 PC가 먼저 저장했으면 409 충돌을 받아 자동 동기화를 멈춘다. 담당자가 설정 화면에서
서버 자료를 다시 받거나 이 PC 자료를 강제로 올릴 때까지 어느 쪽도 조용히 덮어쓰지 않는다.

공유폴더의 `backups`에 SQLite 온라인 백업을 만드는 버튼도 추가했다. 공용 자료는 설비·담당자·
이력·일정·법령·에너지이며 서버 토큰과 PC별 AI 설정은 포함하지 않는다. 토큰은 브라우저와
Git에서 분리하고, LAN 공개는 토큰 없이는 시작할 수 없게 했다. 기본 바인딩은 localhost이며
같은 서버가 화면과 API를 함께 제공한다. 보안 프로그램 우회나 관리자 권한 설치는 하지 않는다.

담당자 통합 대장은 법정선임·유지관리 구분, 부서, 전화, 메일, 재직 상태를 관리한다. 설비는
담당자 ID로 연결되고 화면·엑셀·알림 호환을 위해 이름과 연락처 스냅샷도 함께 유지한다. 담당 설비가
남아 있는 사람은 삭제하지 못한다.

검증은 규칙 98개와 서버 7개가 통과했다. 화면 흐름은 아홉 페이지·56개로 확대했으며 로컬 작업
환경에 브라우저 실행 파일이 없어 PR CI에서 실제 Chromium 검증을 완료하도록 남겼다.

## 13. 설비별 연관법령 직접 추가

내장 후보표에 없는 법령도 현장 판단으로 등록할 수 있어야 했다. 설비 상세의 법령 탭에
「연관법령 직접 추가·수정」 폼을 만들고 법령명, 이 설비와 관련된 이유, 국가법령정보센터 등
출처 URL, 시행일, 적용 조항, 첨부파일을 설비 ID에 연결해 저장하도록 했다.

법령명만 필수로 두되 출처 URL은 HTTP/HTTPS만 허용한다. 같은 설비에 같은 법령명을 다시
입력하면 별도 레코드를 늘리지 않고 기존 문서를 수정한다. 직접 추가한 법령도 자동 후보에서
저장한 법령과 동일하게 내부 DB·공용 동기화·법령 비교검토의 입력 자료로 사용한다.

규칙 98개와 서버 7개는 그대로 통과했고, 실제 화면 검사는 직접 입력과 출처 저장 흐름을 더해
58개로 확대했다.

## 14. 비교 검토표에서 검토기록 자동 작성

비교 검토표의 각 요구사항에 「검토기록에 반영」 버튼을 추가했다. 버튼을 누르면 법령명,
법령 요구사항, 확인일, 설정에 저장된 작업자명, 법령 파일 경로를 검토 기록 폼에 자동으로
채운다. 자동 입력값은 읽기 전용이며 담당자는 검토결과만 입력한다. 이전 기록의 `note`는
검토결과로 계속 표시해 기존 데이터도 잃지 않는다.

요구사항 설명은 저장된 법령 원문에서 조문 번호와 정량 기준을 추출하고, 해당 설비의 용량·압력·
냉난방능력·법정선임관리자·검사주기를 함께 보여 준다. 원문에 조문이나 기준 수치가 없으면 값을
추측하지 않고 「원문 추가 확인 필요」로 명시한다. 자동 비교는 참고자료이며 최종 적합 판정은
담당자가 원문과 현장 설비를 확인해 검토결과에 남긴다.

검증은 규칙 102개, 사내 서버 7개, 화면 흐름 61개로 확대했다.

## 15. 검토기록 요구사항 요약과 전체 글보기

검토기록 목록에서 긴 법령 요구사항 전문을 그대로 펼치지 않고 72자 이내 두 줄 요약으로 표시한다.
옆의 「전체 글보기」 버튼을 누르면 별도 팝업에서 저장된 요구사항 전문을 확인할 수 있다.
표의 각 열 너비와 파일 경로 말줄임도 함께 조정해 설비 상세 화면에서 불필요한 가로 스크롤을 줄였다.
검증은 규칙 102개, 사내 서버 7개, 화면 흐름 63개로 확대했다.

## 16. 완료 이력 자동 반영과 알림 승인 대기함

법정검사 이력을 저장하면 해당 설비의 최근 검사일과 실제 검사비용을 갱신한다. 소모품 교체는
내용에 이름을 타이핑해 연결하던 방식 대신 교체한 품목을 직접 선택하고, 최근 교체일과 실제 비용을
자동 반영한다. 기존 이력은 이전처럼 내용의 소모품 이름을 이용해 다시 반영할 수 있다.

알림 화면에는 승인 대기함을 추가했다. 현재 임박·오늘·기한 초과 항목을 중복 없이 넣고 담당자가
문안과 수신자를 확인한 뒤 승인한다. 승인된 건만 사내 보조 서버의 SMTP 설정으로 발송할 수 있으며,
SMTP가 없거나 보안 승인을 받지 않은 환경은 복사 후 수동 발송완료로 기록한다. SMTP 비밀번호는
브라우저·공용 DB·GitHub에 저장하지 않고 `server/config.local.json`에서만 읽는다.

검증은 규칙 104개, 사내 서버 10개, 화면 흐름 67개로 확대했다.

## 17. 법령 최신본 확인과 개정 영향 검토

설비에 저장된 연관법령이 여러 건이면 「저장 법령 최신본 확인」에서 각 법령을 빠짐없이
개별 조회한다. 국가법령정보센터 API와 사내 서버가 설정된 환경은 최신 원문을 가져오고,
외부 접속이 막힌 환경은 담당자가 최신 파일을 업로드하거나 원문을 붙여넣어 저장하면 같은
비교 절차가 실행된다. 보안 프로그램 우회나 브라우저의 직접 외부 호출은 추가하지 않았다.

원문 갱신 전·후 본문은 `lawVersions`에 보존하며 실제로 달라진 문장만 `lawChanges`에 기록한다.
최신본에 추가된 문장과 이전본에만 있던 문장을 전체 보기로 나눠 표시하되, 문장 변경만으로
법적 의미나 적합 여부를 자동 확정하지 않는다. 최신 원문에 용량·유량·압력·소모전력·냉난방능력·
법정선임관리자·검사주기가 필요한데 설비 값이 비어 있으면 추가 입력 요청 항목으로 표시한다.

각 변경 건은 기존 설비 사양 비교표로 이어지고, 유지관리자에게 보낼 검토 요청을 알림 승인
대기함에 추가할 수 있다. 알림에는 변경 문장 수와 누락 사양이 포함되며 기존 원칙대로 승인 전에는
메일을 보내지 않는다. 담당자가 검토 완료를 누른 경우에만 변경 상태와 설비의 최근 법령 확인일을
갱신한다. 규칙 검증은 108개, 사내 서버 검증은 10개가 통과했다.

## 18. 사내 운영 자동화·복구·OCR·예산·조감도 편집

브라우저를 켜 두지 않아도 `server/run_jobs.bat`를 Windows 작업 스케줄러에서 실행해 법정검사와
소모품 D-30을 확인하고 승인 대기함에 중복 없이 추가하도록 했다. 법령 API가 설정된 환경은 주기적으로
모든 저장 법령을 확인해 변경 전·후 원문, 변경 문장, 누락 설비 사양과 알림을 함께 남긴다. 항목 하나가
실패해도 나머지는 계속 처리하며 실행 상태와 오류는 `job_runs`와 설정 화면에 기록한다.

공용 DB는 백업 목록을 화면에서 조회하고 선택 복원할 수 있다. 복원 직전 현재 DB를 다시 안전 백업하므로
잘못 선택해도 직전 상태로 돌아갈 수 있다. 서버 토큰은 관리자·편집자·읽기 전용으로 분리했고, 설정 변경·
백업·복원은 관리자만, 자료 수정과 자동 점검은 편집자 이상만 실행한다. 토큰 목록은 설정 API로 노출하지 않는다.

에너지 PDF에 글자가 거의 없으면 스캔 문서로 보고, 사내 서버에 승인된 OCR API 키가 있을 때만 보조 추출을
시도한다. OCR이 없거나 실패하면 해당 문서만 건너뛰고 이유를 화면에 남긴다. 비용 화면은 물가상승률·예비비와
검사/소모품 구분 합계를 표시하고 엑셀에도 보정 단가와 최종 예산을 기록한다. 조감도는 실제 이미지를 이 PC에만
보관하고 건물 좌표를 화면에서 편집해 공용 데이터로 저장할 수 있다.

## 19. 복수 법정검사와 다각형 건물 편집

한 설비가 계속사용검사·성능검사처럼 여러 검사를 받을 수 있어 설비의 검사 정보를 배열로 확장했다.
검사명·최근 검사일·주기·비용을 항목별로 추가하며, 알림 대기열·다음 검사 계산·차년도 예산·엑셀에도
각 검사가 별도 항목으로 반영된다. 예전 단일 검사 값은 첫 번째 `정기검사` 항목으로 자동 변환한다.

조감도는 사각형 입력표 대신 `건물 추가` 후 외곽점을 순서대로 찍는 다각형 편집 방식으로 바꿨다.
다각형을 완성하면 건물 목록에 추가되고, 이름 변경 시 연결된 설비 위치도 함께 갱신한다. 기존 사각형
좌표는 네 꼭짓점 다각형으로 자동 변환해 이전 자료를 유지한다.

검증은 규칙 110개, 자동 점검 4개, 사내 서버 13개로 확대했다. 로컬 화면 검사는 실행 파일이 없는
환경에서는 오류를 기록하고 건너뛰며, GitHub CI에서 새 다각형·복수 검사 화면까지 확인한다.

## 20. 메뉴별 이용안내

개요 화면 아래에 있던 「이 도구가 하는 일과 하지 않는 일」은 대시보드의 우선순위를 흐려 삭제했다.
대신 상단 메뉴에 「이용안내」를 추가해 담당자 등록 → 설비 등록 → 일정 관리 → 운영 확장 순서와
개요·설비·담당자·알림·이력·비용·에너지·조감도·설정의 목적과 주요 기능을 각각 설명한다.

자동 분석이 법적 적합 여부를 확정하지 않는다는 점, 검사주기는 최신 법령과 설비 사양으로 최종
확인해야 한다는 점, 외부 전송과 메일 발송 전 보안·수신자 확인이 필요하다는 원칙도 별도 카드에 남겼다.
페이지 최하단에는 실제 메일, OCR·법령·외부 AI 인증, 공유폴더 권한, 현장 자료, Windows 자동 점검,
로컬 화면 검사처럼 회사 환경에 따라 추가 설정이 필요한 항목과 현재 대체 처리 방법을 함께 표시했다.

규칙 108개, 자동 점검 3개, 사내 서버 13개 검사가 통과했다. 로컬 Playwright는 실행 파일이 없어 화면 검사
71개를 실행하지 못했으며, 코드는 건너뛰지 않고 CI에서 실행하도록 남겼다. 오류 원인과 검증 대체 경로를 기록한 뒤
나머지 빌드·배포를 계속 진행했다.

## 21. 이력 검사주기·Excel 등록양식·법령 질의 도우미

법정검사 이력 목록과 설비 상세 이력에 선택한 검사명과 등록 주기를 함께 표시한다. 예전 이력처럼 검사 ID가
없는 자료는 해당 설비의 첫 번째 검사 항목을 사용하되, 주기가 없으면 숫자를 추정하지 않고 `주기 미입력`으로 표시한다.

설비 화면에는 `양식 다운로드`를 추가했다. 양식은 `설비등록양식`, `검사항목양식`, `작성안내` 세 시트로 구성되며
같은 설비번호의 검사를 여러 줄 작성하면 복수 검사항목으로 가져온다. 설비번호가 기존 대장과 같으면 관련 이력·문서를
삭제하지 않고 기본정보와 양식에 입력한 검사만 갱신하며, 신규 번호는 새 설비로 등록한다.

개요 소제목은 사내 보고 화면에 맞게 `시설 운영 현황`, `다가오는 점검·교체 일정`, `설비·법령 정보 보완 필요`로
바꿨다. 하단의 법령 질의 도우미는 질문에서 관련 법령 후보와 내부 저장 원문을 찾는다. 국가법령정보센터 OC 인증값과
사내 서버가 있으면 최신 원문을 조회하고, 승인된 로컬·외부 AI가 연결된 경우에만 해당 원문 근거로 상세 답변한다.
원문 또는 연결이 없으면 법령명과 공식 검색 링크까지만 안내하고 기준 숫자나 적용 여부를 임의로 만들지 않는다.
